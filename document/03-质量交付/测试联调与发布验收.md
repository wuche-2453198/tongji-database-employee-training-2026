# 测试联调与发布验收

## 1. 质量原则

质量验收以可复现证据为准，不以“本机运行过”作为完成。每项任务必须能从 PR、Swagger、HTTP 用例、构建日志、数据库执行日志或页面截图中找到验收证据。

缺陷优先级：

| 级别 | 定义 | 发布处理 |
| --- | --- | --- |
| P0 | 系统不可启动、数据损坏、安全泄露、主流程完全中断 | 立即停止集成，必须清零 |
| P1 | 核心规则、权限或主要页面错误，但存在临时绕行 | D14 前必须清零 |
| P2 | 非主流程功能或体验问题 | 明确负责人和后续计划，可评审接受 |
| P3 | 文案、样式或低影响建议 | 记录后按时间处理 |

## 2. 模块完成定义（DoD）

后端模块合并前必须提供：

- Controller、Service、Repository、请求/响应/查询 DTO。
- Swagger 中可见且与冻结路径、字段、枚举一致。
- 至少 1 个正常 HTTP 用例和 2 个关键失败用例。
- 401、403、404、409 中与模块相关的错误已验证。
- 多表写入使用事务，用户输入使用参数化 SQL。
- 涉及数据库结构时提供新迁移并完成空库或升级验证。

前端业务页面合并前必须提供：

- 路由、页面入口、真实 API 调用和权限条件。
- 加载、空数据、提交中、成功、失败和 403 状态。
- 表单格式校验、服务端业务错误展示和防重复提交。
- 刷新后的登录态行为合理，不硬编码 base URL、字段或枚举。
- 桌面常用视口下文本、表格、表单和操作按钮不重叠。

数据库变更完成前必须提供：迁移文件、执行顺序、空 Schema 日志、升级影响、验证 SQL；种子数据不得替代业务用例验证。

## 3. 测试矩阵

| 模块 | 正常场景 | 必测失败/边界 |
| --- | --- | --- |
| 认证 | 四角色登录、获取当前用户 | 错误密码、离职账号、无 Token 401、越权 403 |
| 组织 | 员工/部门/黑名单 CRUD 或状态操作 | 重复登录名、预算为负、重复生效黑名单、员工物理删除不可用 |
| 课程 | 新建草稿、编辑、发布、关闭、容量摘要 | 缺必填、时间反向、预算不足、重复发布、发布后改预算 |
| 申请 | 提交、主管通过/驳回、HR 备案 | 重复活跃申请、未发布课程、跨部门审批、跳步和重复审批 |
| 报名 | HR_FILED 后报名、取消后重报、查询 | 未备案、离职、黑名单、满员、课程已开始、重复有效报名 |
| 签到 | 正常/迟到/手工签到、缺勤、完成 | 重复签到、未报名签到、开课前缺勤、未签到完成、学时负数 |
| 评分 | 完成后评分、HR 复核、平均分 | 未完成评分、分数越界、重复评分、越权查看 |
| 测试 | 开课前 PRE、完成后 POST、提升值 | 错误时点、分数越界、重复类型、非 HR/管理员录入 |
| 证书 | 符合资格后发证、查询、提醒 | 未完成、缺合格 POST、重复发证、证书编号冲突 |
| 数据库 | 空库迁移、种子、验证、备份恢复 | 孤儿外键、重复活跃记录、预算透支、identity 与种子冲突 |

报名至少增加一次并发测试：两个请求争抢最后一个名额，最终只能有一个成功，另一个返回 409，课程人数不得超过上限。

## 5. 主流程验收脚本

1. 管理员登录，创建或确认部门、员工、讲师和草稿课程。
2. 管理员发布课程，验证部门已用预算增加、余额正确。
3. 员工登录并提交申请；重复提交被 409 拦截。
4. 其他部门主管无法审批，本部门主管审批通过。
5. HR 完成备案；员工使用该申请报名。
6. 另一个黑名单员工报名失败；重复有效报名失败。
7. HR/管理员执行签到，验证迟到分钟、扣减学时和实际学时。
8. 课程结束后完成培训；未签到报名不可完成。
9. 员工提交评分；HR 按正确时点录入 PRE/POST 成绩。
10. HR 生成证书；第二次生成被 409 拦截。
11. 员工只能查询自己的申请、报名和证书；HR/管理员可以跨部门查询。
12. 执行数据库验证 SQL，确认无超卖、重复、孤儿外键和预算透支。

这条验收必须使用本轮新创建的数据，不得直接展示种子中已经完成的历史流程。

## 6. 日常集成和 PR 门禁

每日 17:30 在 `develop` 执行：

1. 后端 restore/build/test，启动后检查 `/api/health` 和 `/api/health/db`。
2. 前端 install/build，验证登录、路由和关键页面加载。
3. 有数据库变更时从空 Schema 或指定前一版本执行迁移和种子。
4. 运行当前已接入模块的 `tests/api/*.http` 主路径和关键失败用例。
5. 把结果、失败责任人和处理时限写入集成记录。

PR 合并条件：构建和测试通过、Swagger 可见、迁移可执行、接口变化已通知并同步前端、无敏感信息、至少一名成员审查。D3、D8、D12、D14 强制执行全量冒烟；红灯时黄茁宇暂停相关合并。

## 7. 缺陷记录与升级

每条联调问题包含：标题、环境、角色/账号类型、接口或页面、前置数据、复现步骤、期望结果、实际结果、traceId、优先级、责任人、状态、关联 PR 和验证结果。

状态统一为 `OPEN -> IN_PROGRESS -> READY_FOR_VERIFY -> CLOSED`，不能由开发者在未验证时直接关闭。跨模块问题默认归属最先违反契约的一方；无法判断时由黄茁宇在当日指定主责和协作人。

## 8. 发布验收

发布候选必须同时满足：

- 从空 Schema 依次执行 `V001`、`V002`、`V003`、`S001`、`S002`、`S003` 成功，日志已归档。
- 使用 `TRAINING_APP` 完成数据库健康检查和全部业务 CRUD。
- 四角色登录、401、403、409 可复现，前端提示与行为正确。
- 预算不足、发布后改预算、越权审批、黑名单、满员、重复报名、重复签到、未完成发证全部被拒绝。
- 主流程在新数据上从课程发布走到证书查询，不手工改库。
- 后端和前端构建通过，P0/P1 缺陷为 0，P2 均有接受记录或计划。
- 仓库不含密码、私钥、Token、个人路径、编译产物和本地日志。
- 新环境按根 README 可部署；`demo-ready` 备份已完成恢复演练。
