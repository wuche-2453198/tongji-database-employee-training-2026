# 前端工作的执行步骤与输出成果

## 1. 文档目的

本文档用于明确企业内部培训管理系统前端设计工作的职责边界、执行阶段、具体步骤、输出成果和验收标准，并作为前端设计负责人提交给 AI 分阶段执行的任务依据。

当前接口尚未冻结，前端工作以需求梳理、信息架构、页面设计、交互设计、权限设计、组件规范和 Mock 数据设计为主。当前不创建正式前端工程，不编写业务代码，不进行真实接口联调；接口冻结后再进行字段映射、设计修订和联调验收。

## 2. 已冻结的前端技术路线

本项目前端统一采用以下技术路线：

- 核心框架：Vue 3。
- 开发语言：TypeScript。
- 构建工具：Vite。
- 组件编码方式：Composition API 和 `<script setup>`。
- 路由管理：Vue Router。
- 全局状态管理：Pinia。
- 应用形态：前后端分离的单页后台管理系统（SPA）。
- 数据策略：接口尚未冻结期间，使用 Mock 数据完成页面设计与交互验证；真实接口确定后，再进行字段映射和前后端联调。

上述技术路线现在作为后续前端开发的统一依据。具体依赖版本、UI 组件库、HTTP 客户端和测试工具在创建工程前另行确认。

## 3. 前端工作边界

### 3.1 接口未冻结时可以执行

- 梳理用户角色、业务范围和页面范围。
- 建立系统信息架构、菜单结构和页面层级。
- 规划前端路由，但暂不编写 Vue Router 配置代码。
- 制作业务流程图、低保真线框图和高保真界面稿。
- 制作可点击交互原型。
- 设计公共布局、公共组件和视觉规范。
- 设计页面的加载、空数据、失败、无权限等状态。
- 建立角色、菜单、页面和操作权限矩阵。
- 编写页面字段需求和 Mock 数据结构草案。
- 整理需要后端确认的接口、字段和业务规则问题。
- 组织设计评审并记录评审结论。

### 3.2 接口未冻结时暂不执行

- 不创建 Vue 3 + TypeScript + Vite 工程。
- 不安装 Vue Router、Pinia 或其他依赖。
- 不编写 Vue 页面、组件、状态管理或路由代码。
- 不连接真实后端接口或 Oracle 数据库。
- 不最终锁定尚未由后端确认的请求字段、响应字段和错误码。
- 不将 Mock 数据结构直接视为最终接口结构。
- 不进行真实登录、权限校验和业务联调。

## 4. 前端工作的执行阶段

前端设计工作划分为 5 个执行阶段，共包含 12 个具体步骤。每个阶段完成后必须先进行评审，确认通过后再进入下一阶段。

| 阶段 | 对应步骤 | 阶段目标 | 主要输出成果 | 进入下一阶段的条件 |
| --- | --- | --- | --- | --- |
| 第一阶段：需求与架构 | 步骤 1～4 | 明确需求范围、角色权限、信息架构、菜单、页面和路由 | 需求清单、权限矩阵、信息架构图、菜单表、页面清单、路由规划表 | 页面范围、角色权限和导航结构完成初审 |
| 第二阶段：流程与线框 | 步骤 5～6 | 串联核心业务流程并完成 P0 页面结构设计 | 业务流程图、P0 低保真线框图、页面交互说明 | 业务流程和 P0 页面结构完成评审 |
| 第三阶段：规范与 Mock | 步骤 7～9 | 建立视觉、组件、页面状态和临时数据规范 | 视觉规范、组件规范、状态规范、Mock 数据字典 | 视觉方向、组件规则和 Mock 场景完成评审 |
| 第四阶段：高保真原型 | 步骤 10 | 形成可按角色演示的 P0 高保真交互原型 | P0 高保真稿、可点击原型、演示路径 | 页面视觉与交互完成评审 |
| 第五阶段：接口衔接与交付 | 步骤 11～12 | 整理接口需求、完成字段映射、评审并交付设计 | 接口需求表、字段映射表、评审记录、最终设计包 | 真实接口冻结并完成最终设计验收 |

### 4.1 分阶段执行规则

```text
AI 执行当前阶段
→ 输出本阶段成果
→ 标记“已确认”“暂定”和“待确认”内容
→ 相关负责人评审
→ 根据意见修改
→ 阶段成果确认
→ 进入下一阶段
```

- AI 不应在没有评审的情况下连续完成全部 5 个阶段。
- 未由项目文档或相关负责人确认的字段、权限和业务规则必须标记为“暂定”或“待确认”。
- 第一至第四阶段可以基于 Mock 数据推进；第五阶段中的最终字段映射需要等待真实接口冻结。
- 前端设计负责人只提出前端需求，不替数据库或后端负责人决定最终实现。

## 6. 页面范围与优先级

### 6.1 P0：核心演示流程

P0 页面优先完成设计，用于验证完整业务主流程：

1. 登录页。
2. 首页或控制台。
3. 课程列表页。
4. 课程详情页。
5. 提交培训申请页。
6. 我的申请页。
7. 主管审批页。
8. HR 备案页。
9. 我的报名页。
10. 签到管理页。
11. 我的证书页。
12. 证书管理页。
13. 证书详情页。
14. 403 无权限页。
15. 404 页面。

### 6.2 P1：基础数据维护

1. 员工管理页。
2. 部门预算管理页。
3. 讲师管理页。
4. 课程管理页。
5. 课程新增与编辑页。

### 6.3 P2：完整性与增强功能

1. 黑名单管理页。
2. 讲师评分页。
3. 测试成绩录入页。
4. 测试成绩查询页。
5. 统计或展示类页面。

## 7. 具体执行步骤与输出成果

### 步骤 1：确认设计输入和边界

执行内容：

1. 阅读数据库设计文档、项目分工计划、项目开发规范和第 0 阶段目标。
2. 提取四类角色、核心业务模块、主要业务状态和操作规则。
3. 标记文档中存在冲突、不明确或需要后端确认的内容。
4. 确认当前设计工作只交付设计成果，不创建正式工程。

输出：

- 前端需求清单。
- 设计疑问清单。
- 当前阶段范围说明。

### 步骤 2：建立角色权限矩阵

执行内容：

1. 横向列出员工、部门主管、HR、管理员四类角色。
2. 纵向列出菜单、页面和关键操作。
3. 标记查看、新增、编辑、审批、备案、签到、生成证书等权限。
4. 区分“菜单不可见”“页面不可进入”和“按钮不可操作”三种权限表现。

输出：

- 角色—菜单权限矩阵。
- 角色—页面权限矩阵。
- 角色—操作权限矩阵。

### 步骤 3：设计信息架构和菜单

执行内容：

1. 将功能划分为首页、培训中心、我的培训、审批管理、培训运营和系统管理等导航分组。
2. 确定一级菜单、二级菜单和页面入口。
3. 根据角色权限形成不同角色的菜单视图。
4. 确定页面标题、面包屑和返回关系。

输出：

- 系统信息架构图。
- 菜单结构表。
- 各角色菜单示意图。

### 步骤 4：规划页面和路由

执行内容：

1. 为每个页面定义页面名称和建议路径。
2. 标记页面所属布局、是否需要登录、允许访问角色和上级页面。
3. 标记列表页、详情页、新增页和编辑页之间的跳转关系。
4. 规划 403、404 和登录失效后的跳转规则。

路由规划表至少包含：

| 字段 | 说明 |
| --- | --- |
| 页面名称 | 用户界面展示名称 |
| 建议路径 | 例如 `/courses`、`/my/requests` |
| 页面类型 | 列表、详情、表单、公共页面 |
| 所属布局 | 登录布局或主布局 |
| 登录要求 | 是否必须登录 |
| 允许角色 | 员工、主管、HR、管理员 |
| 上级页面 | 面包屑和返回目标 |

输出：

- 页面清单。
- 路由规划表。
- 页面跳转关系图。

### 步骤 5：设计核心用户流程

执行内容：

围绕以下主流程分别绘制角色泳道图或用户流程图：

```text
管理员维护基础数据并发布课程
→ 员工提交培训申请
→ 部门主管审批
→ HR 备案
→ 员工报名
→ HR 或管理员签到
→ 员工评分
→ HR 录入测试成绩
→ HR 生成证书
→ 员工查看证书
```

每个节点必须明确：

- 当前角色。
- 入口页面。
- 用户动作。
- 前置状态。
- 成功结果。
- 失败或禁止操作的反馈。
- 下一步页面或状态。

输出：

- 完整业务主流程图。
- 申请审批流程图。
- 报名签到流程图。
- 评分、测试与证书流程图。

### 步骤 6：制作低保真线框图

执行内容：

1. 先完成公共页面和所有 P0 页面。
2. 确定页面布局、信息层级、搜索条件、表格字段和主要按钮位置。
3. 为表单标记字段类型、必填项和暂定校验要求。
4. 为关键按钮标明显示条件和点击结果。
5. 暂不追求颜色、图标和精细视觉效果。

输出：

- 公共页面低保真稿。
- P0 页面低保真稿。
- 页面说明和交互标注。

### 步骤 7：建立视觉与组件规范

执行内容：

1. 确定后台管理系统的整体视觉方向。
2. 定义主色、辅助色、文字色、边框色和背景色。
3. 定义成功、警告、错误、禁用和业务状态颜色。
4. 定义字体层级、间距、圆角、阴影和页面宽度。
5. 统一按钮、表格、分页、搜索区、表单、弹窗和抽屉样式。
6. 在高保真设计前确认是否采用 Element Plus 或其他 UI 组件库作为视觉基础。

输出：

- 视觉规范。
- 公共组件规范。
- 业务状态展示规范。

### 步骤 8：设计页面状态和异常反馈

每个 P0 页面至少设计以下状态：

- 初始状态。
- 加载中。
- 正常有数据。
- 空数据。
- 搜索无结果。
- 加载失败。
- 提交中。
- 提交成功。
- 表单校验失败。
- 无权限。
- 登录过期。
- 业务冲突，例如重复报名、课程已满或状态不允许操作。

输出：

- 页面状态清单。
- 状态页面或组件示意图。
- 提示文案规范。

### 步骤 9：建立 Mock 数据字典

执行内容：

1. 根据页面展示需要，定义临时数据实体和字段。
2. 为员工、角色、讲师、课程、申请、报名、签到、评分、测试和证书准备示例数据。
3. 统一暂定枚举值，不在不同页面重复定义不同名称。
4. 准备正常、空数据、失败、无权限和业务冲突等场景。
5. 所有未由后端确认的字段标记为“暂定”。

Mock 数据字典至少包含：

| 字段 | 说明 |
| --- | --- |
| 实体名称 | 例如课程、培训申请 |
| 字段名称 | 前端暂定字段名 |
| 类型 | string、number、boolean、date 等 |
| 是否必填 | 页面或业务是否需要 |
| 示例值 | 用于原型展示的值 |
| 枚举说明 | 状态字段的可选值 |
| 确认状态 | 暂定或后端已确认 |

输出：

- Mock 数据字典。
- Mock 场景清单。
- 待后端确认字段清单。

### 步骤 10：制作高保真稿和可点击原型

执行内容：

1. 低保真稿评审通过后再制作高保真页面。
2. 将公共视觉和组件规范应用到所有 P0 页面。
3. 使用 Mock 数据展示真实业务内容。
4. 按不同角色建立原型入口。
5. 串联登录、申请、审批、备案、报名、签到和证书主流程。

输出：

- P0 高保真页面稿。
- 按角色组织的可点击交互原型。
- 演示路径说明。

### 步骤 11：整理接口需求和待确认事项

执行内容：

1. 按页面列出所需的查询、新增、编辑和状态流转接口。
2. 根据设计稿提出页面必须使用的字段。
3. 标记分页、搜索、排序、枚举和权限需求。
4. 将 Mock 字段与后端最终字段逐项对照。
5. 记录差异，但在接口冻结前不擅自认定最终结构。

输出：

- 页面—接口依赖表。
- 前端字段需求表。
- 接口待确认问题清单。

### 步骤 12：设计评审和最终交付

执行内容：

1. 组织前端内部评审，检查页面一致性和组件复用。
2. 邀请业务模块负责人检查流程和业务规则。
3. 邀请后端负责人检查字段可实现性、状态和权限。
4. 邀请项目负责人确认页面优先级和演示流程。
5. 修改设计并记录最终结论。

输出：

- 设计评审记录。
- 问题与修改清单。
- 最终前端设计交付包。

## 8. 总体执行顺序

任务按照依赖关系执行，不建议直接从高保真界面开始：

```text
需求范围梳理
→ 角色权限矩阵
→ 信息架构和菜单
→ 页面与路由规划
→ 核心业务流程
→ P0 低保真线框图
→ 视觉与组件规范
→ 页面状态设计
→ Mock 数据字典
→ P0 高保真与交互原型
→ 接口需求清单
→ 设计评审与交付
```

P0 设计评审通过后，再按照同一规范设计 P1 和 P2 页面。

## 9. 输出成果目录建议

设计成果可以统一整理为以下结构；文件应随着各执行阶段逐步创建，不要求在第一阶段一次性建立全部文件：

```text
document/frontend-design/
├── 01-前端需求清单.md
├── 02-角色权限矩阵.md
├── 03-信息架构与菜单.md
├── 04-页面与路由规划.md
├── 05-核心业务流程.md
├── 06-视觉与组件规范.md
├── 07-页面状态规范.md
├── 08-Mock数据字典.md
├── 09-接口需求与待确认事项.md
├── 10-设计评审记录.md
└── assets/
    ├── wireframes/
    ├── high-fidelity/
    └── flows/
```

如果设计稿使用 Figma、即时设计、MasterGo、Axure 等外部工具，应在对应 Markdown 文档中记录原型链接、版本、负责人和最后更新时间。

## 10. 接口冻结后的衔接工作

接口冻结后，前端设计负责人需要配合完成以下工作：

1. 将 Mock 字段映射到真实 API 字段。
2. 核对分页结构、错误结构和状态枚举。
3. 核对登录接口、Token 传递方式和当前用户接口。
4. 核对角色权限与后端授权规则。
5. 修正因真实业务约束产生的页面和交互差异。
6. 将设计交付给开发人员实现。
7. 参加前后端联调和 UI 还原检查。

## 11. 前端设计工作最终完成标准

满足以下条件后，可认为本项目前端设计工作完成并具备开发、联调和验收依据：

- 前端技术路线已被记录并通知项目成员。
- 四类角色的菜单、页面和操作权限已经形成初版矩阵。
- 页面清单、优先级和路由规划已经明确。
- 核心业务主流程可以通过流程图完整说明。
- 登录、主布局及所有 P0 页面已有低保真设计。
- P0 页面已有统一的视觉规范和高保真原型。
- 关键页面覆盖加载、空数据、失败、无权限和业务冲突状态。
- Mock 数据能够支撑不同角色和核心业务场景的原型演示。
- 每个 P0 页面都有接口需求和待确认字段清单。
- 设计已经过前端、后端、业务模块和项目负责人评审。
- 尚未确定的内容均明确标记为“暂定”，没有被误认为最终接口约定。
