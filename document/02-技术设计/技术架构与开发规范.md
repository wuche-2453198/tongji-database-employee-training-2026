# 技术架构与开发规范

## 1. 冻结技术栈

| 层 | 技术 | 执行口径 |
| --- | --- | --- |
| 架构 | B/S、前后端分离 | 浏览器只访问 HTTP API，前端不得连接 Oracle |
| 后端 | .NET 8、ASP.NET Core Web API | 单体模块化项目，首期不拆微服务 |
| 数据访问 | Dapper、Oracle.ManagedDataAccess.Core | 参数化 SQL；多表写入使用事务 |
| 认证与接口 | JWT Bearer、Swagger/OpenAPI | 四角色授权；开发期参考接口建议，验收时以实现生成的 Swagger/OpenAPI 为准 |
| 前端 | Vue 3、TypeScript、Vite | Vue Router、Pinia、Axios、Element Plus |
| 数据库 | Oracle 19c+，推荐 Free 23ai / XE 21c | `AL32UTF8`、`CHAR` 长度语义；物理结构以迁移脚本为准 |

认证固定使用 JWT。首期不做服务端 Token 吊销，因此退出登录由前端清除 Token 和用户状态完成，不提供具有虚假安全语义的 `/api/auth/logout`。如后续增加刷新令牌或吊销表，再补充服务端退出接口。

## 2. 架构与模块边界

```text
Vue 3 Browser App
  -> ASP.NET Core Controllers
  -> Application Services（业务、权限数据范围、事务）
  -> Repositories（Dapper/Oracle 参数化 SQL）
  -> Oracle TRAINING_OWNER Schema
```

- Controller 负责 HTTP 参数、调用 Service 和返回统一结果，不写 SQL 或复杂业务。
- Service 负责状态机、业务校验、数据范围权限和事务边界。
- Repository 只负责数据库读写，不判断用户角色，不拼接用户输入。
- DTO 与数据库实体分离，Controller 不直接返回 Entity。
- 模块间优先调用公开 Service 接口；不得引用其他模块 Repository 或修改其内部状态。
- 员工 CRUD 归组织模块；认证模块只读取认证字段并拥有角色关联逻辑。

## 4. API 契约

> 本节的 URL、HTTP 方法和 DTO 命名是推荐风格，用于减少协作差异，不是模块开工门槛。模块可根据实现调整，但最终验收前必须形成准确的 Swagger/OpenAPI 和文档，并保证前后端与测试使用同一口径。

### 4.1 URL 和 HTTP 方法

- 路径统一使用 `/api/{resource}`，资源名为小写复数，多词用连字符。
- `GET` 查询，`POST` 创建，`PUT` 完整更新，`PATCH` 局部更新或显式业务动作。
- 状态动作放在资源 ID 后，例如 `PATCH /api/training-requests/{id}/dept-approve`。
- 员工不提供物理删除接口，仅使用 `PATCH /api/employees/{id}/status` 改为 `RESIGNED`。
- 固定角色为只读种子，只提供 `GET /api/roles`，首期不做角色 CRUD。

### 4.2 成功、失败与分页

```json
{
  "success": true,
  "message": "ok",
  "data": {},
  "traceId": "string"
}
```

```json
{
  "success": false,
  "message": "课程容量已满",
  "errors": [
    { "field": "courseId", "message": "该课程已达到最大报名人数" }
  ],
  "traceId": "string"
}
```

```json
{
  "success": true,
  "message": "ok",
  "data": {
    "items": [],
    "page": 1,
    "pageSize": 20,
    "total": 100
  },
  "traceId": "string"
}
```

| 状态码 | 用途 |
| --- | --- |
| `200` | 查询或更新成功 |
| `201` | 创建成功 |
| `400` | 参数错误或状态流转不合法 |
| `401` | 未提供或 Token 失效 |
| `403` | 角色或数据范围无权限 |
| `404` | 资源不存在 |
| `409` | 重复申请/报名/证书、满员等资源冲突 |
| `500` | 未处理的服务端错误，不返回 SQL 或连接信息 |

### 4.3 契约变更

开发期间允许先实现、后整理接口文档。一旦模块进入联调，当前实现生成的 Swagger/OpenAPI 就是请求和响应字段的当前来源；后续变更需在 PR 中说明影响，并在模块最终验收前同步 DTO、前端类型、测试和文档。前端不得通过猜测多个字段名规避契约不一致。

## 5. 后端规范

> 新增业务模块前必读 `src/backend/TrainingManagement.Api/Templates/BackendModuleTemplate.md`——含 Controller/Service/Repository 标准形态、数据范围权限实现方式、BusinessException 使用口径、Dapper 硬性规则(列名对照 DDL、保留字、分页)与提交前自查清单。

```text
TrainingManagement.Api/
├── Controllers/
├── Services/Interfaces/
├── Services/Implementations/
├── Repositories/Interfaces/
├── Repositories/Implementations/
├── Dtos/{Module}/
├── Entities/
├── Common/
├── Middlewares/
└── Program.cs
```

- 类、方法使用 PascalCase；私有字段使用 `_camelCase`；异步方法以 `Async` 结尾；接口以 `I` 开头。
- DTO 使用 `CreateCourseRequest`、`UpdateCourseRequest`、`CourseQuery`、`CourseResponse` 格式。
- SQL 必须参数化；写操作返回影响行数，新建操作返回生成 ID。
- 未知异常统一转换为 500；业务冲突使用业务异常转换为 400/409。
- 课程发布、报名、签到/完成和发证等跨表操作必须使用显式事务。
- 更新状态时同时校验当前状态，必要时使用行锁或带旧状态条件的 `UPDATE` 防止并发覆盖。
- 日志至少覆盖登录、课程发布、审批/备案、签到、完成和发证；日志包含 `traceId`、操作者 ID、资源 ID 和结果，不记录密码或 Token。

## 6. 前端规范

```text
src/
├── api/
├── assets/
├── components/
├── layouts/
├── router/
├── stores/
├── types/
├── views/
└── main.ts
```

- 所有请求通过统一 Axios 客户端；base URL 来自环境变量，不在组件中硬编码。
- Token 和当前用户由认证 Store 维护；401 清状态并跳登录，403 显示无权限页。
- 路由 `meta` 和菜单按角色控制展示，但真实授权必须由后端完成。
- 数据库存英文枚举，前端在一个公共映射中转换中文，不在页面散落状态字符串。
- 每个列表和表单处理加载、空数据、提交中、成功、失败和无权限状态。
- 表单先做格式校验，后端仍是业务规则最终裁决者；409 等业务冲突展示服务端 message。
- 彭浩负责业务页面，李司翰负责公共布局、路由、Store、API 客户端和公共组件；业务页不得绕开公共层。

## 7. Oracle 实现规范

物理结构和迁移顺序见 [Oracle 数据库设计与 DDL](Oracle数据库设计与DDL.md)。工程侧遵守以下规则：

- 对象名使用大写下划线；约束使用 `PK_`、`FK_`、`UQ_`、`CK_`，索引使用 `IDX_`/`UQ_`。
- 主键使用 `NUMBER ... AS IDENTITY`；是否值为 `VARCHAR2(1)` 的 `Y/N`；状态存英文枚举。
- 事件时间使用 `TIMESTAMP(0)`，日历日期使用 `DATE`；数据库与应用统一 `Asia/Shanghai` 时区；金额使用明确精度的 `NUMBER(p,2)`。
- `TRAINING_OWNER` 执行迁移，`TRAINING_APP` 仅运行应用；连接后设置当前 Schema。
- 所有数据库变更必须脚本化。已经在共享环境执行的版本迁移不可原地修改，只能新增下一版本。
- 不使用数据库触发器同步预算、签到或报名状态；这些跨表业务由 Service 的同一事务明确完成。

## 8. Git 与 PR

| 分支 | 用途 |
| --- | --- |
| `main` | 稳定、可演示版本 |
| `develop` | 日常集成和里程碑验收 |
| `feature/{module}-{topic}` | 单一模块或主题开发 |

提交格式为 `类型(模块): 简短说明`，类型使用 `feat`、`fix`、`docs`、`test`、`refactor`、`chore`。示例：`feat(course): add publish endpoint`。

PR 必须说明变更范围、依赖、数据库/API 影响、验证结果和风险。至少一名其他成员审查；涉及数据库、公共后端、公共前端或全局文档时，对应维护人必须审查。禁止直接把未验证功能推入 `develop` 或绕过负责人修改其他模块。

## 9. 配置与安全

- 连接串和 JWT 密钥使用环境变量或不入库的本地配置；仓库只提交 `.env.example` / `appsettings` 占位符。
- 测试账号可写入说明，但必须使用专用测试密码和脱敏数据。
- 不提交真实数据库密码、服务器账号、私钥、Token、个人绝对路径、日志、截图临时文件或 IDE 缓存。
- `.gitignore` 至少覆盖 `.DS_Store`、`.idea/`、`.vscode/`、`.vs/`、`bin/`、`obj/`、`node_modules/`、`dist/`、`logs/`、`*.log`、`*.user`、`*.suo`、`appsettings.Local.json`、`.env.local`。
- 管理操作全部后端授权；密码只存 BCrypt 哈希；数据库异常不原样返回前端。

## 10. 文档同步

- 根 README 维护启动方式；文档中心维护执行规则；数据库 README 维护 Oracle 操作；模块验收时由 Swagger/OpenAPI 和相关文档记录最终 API 字段。
- 规则不得复制到多个文件。同一主题只改其权威来源，并由其他文档链接引用。
- 技术栈、业务边界、字段、枚举或启动方式改变时，代码 PR 必须同步文档。接口开发过程可分步记录，但在模块最终验收或最终交付 PR 前必须补齐。
