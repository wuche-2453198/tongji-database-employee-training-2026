# 企业内部培训管理系统项目分工计划

## 1. 文档目标

本文档用于指导十人小组从数据库设计阶段进入系统实现阶段，重点明确：

- 每位成员负责的模块边界。
- 每个模块需要完成的具体子任务。
- 每个成员需要交付的代码、接口、页面、脚本和文档。
- 各模块之间的依赖关系和联调顺序。
- 第一阶段必须完成的最小可运行系统目标。

项目技术约束如下：

- 系统采用 B/S 架构。
- 后端必须使用 C#，建议使用 ASP.NET Core Web API。
- 数据库必须使用 Oracle，并部署在云服务器上。
- 系统以现有数据库设计文档中的 13 张表为核心数据模型。

## 2. 项目总体实现范围

本系统需要实现企业内部培训管理的完整基础流程：

1. 管理员工、部门、角色、讲师、课程等基础数据。
2. 员工提交培训需求申请。
3. 部门主管审批培训申请。
4. HR 完成备案。
5. 员工报名已发布课程。
6. 培训签到并计算实际学时。
7. 员工进行讲师评分。
8. 记录训前、训后测试成绩。
9. 培训完成后生成证书。
10. 管理黑名单、权限和基础演示数据。

## 3. 推荐架构与模块边界

```mermaid
flowchart LR
    Browser["浏览器"] --> Frontend["前端应用"]
    Frontend --> Api["C# ASP.NET Core Web API"]
    Api --> Service["业务服务层"]
    Service --> Repository["数据访问层"]
    Repository --> Oracle["云服务器 Oracle 数据库"]
```

- 演示数据是否能支撑完整业务链路。

#### 4.1.4 验收标准

- 项目能够在统一 README 指导下启动。
- 全流程演示能够连续完成。
- 每位成员的贡献边界清晰可说明。
- 所有核心接口均能在 Swagger 或接口文档中找到。
- 最终提交材料完整。

#### 4.4.4 业务规则

- 员工状态建议统一为 `ACTIVE`、`RESIGNED`。
- 黑名单状态建议统一为 `ACTIVE`、`RELEASED`。
- 员工离职后不能提交新申请和报名课程。
- 黑名单生效中的员工不能报名新课程。
- 部门预算的剩余预算应由年度预算减已用预算得到，避免前后端各自计算不一致。

#### 4.4.5 前端配合内容

- 员工管理列表页。
- 员工新增/编辑表单。
- 部门预算列表和编辑表单。
- 黑名单列表和解除操作按钮。

#### 4.4.6 验收标准

- 员工、部门、黑名单主要接口均可在 Swagger 中测试。
- 能通过接口创建员工并分配到部门。
- 黑名单生效后，报名模块能够查询并阻止报名。
- 提供至少 5 名员工、3 个部门、1 条黑名单测试数据。

| REQ-06 | 主管驳回 | 记录驳回意见，状态变为 `DEPT_REJECTED` | `PATCH /api/training-requests/{id}/dept-reject` |
| REQ-07 | HR 备案 | 主管通过后 HR 备案，状态变为 `HR_FILED` | `PATCH /api/training-requests/{id}/hr-file` |
| REQ-08 | 状态流转校验 | 禁止跳过主管审批直接 HR 备案，禁止重复审批 | Service 层规则 |
| REQ-09 | 申请统计 | 统计待审批、已通过、已驳回、已备案数量 | 可选接口 |

#### 4.6.4 业务规则

- 只有在职员工可以提交申请。
- 只有已发布课程可以被申请。
- 同一员工对同一课程原则上不允许重复提交待处理申请。
- `PENDING` 只能进入 `DEPT_APPROVED` 或 `DEPT_REJECTED`。
- `DEPT_APPROVED` 只能进入 `HR_FILED`。
- `DEPT_REJECTED` 不能继续备案。
- 主管和 HR 角色权限由后端权限模块统一判断。

#### 4.6.5 前端配合内容

- 提交申请表单。
- 主管审批列表页。
- HR 备案列表页。
- 申请详情页展示审批意见。

#### 4.6.6 验收标准

- 一条申请可以完整走完“提交 - 主管通过 - HR 备案”。
- 驳回申请不能继续备案。
- 无权限用户不能调用审批接口。
- 提供至少 5 条申请测试数据，覆盖待审批、通过、驳回、备案状态。
