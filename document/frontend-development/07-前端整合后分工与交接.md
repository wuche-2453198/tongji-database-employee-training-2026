## 3. 分工原则

1. 李司翰负责“前端平台和公共基础”，彭浩负责“业务页面和业务联调”。
2. 一个页面只能有一个实现主责，不再并行维护两套业务页面。
3. Figma 是页面结构、视觉和交互基线；开发分工不导致重新拆分或重绘 Figma。
4. 彭浩维护现有 Figma 对齐业务页面，不恢复旧分支中未按 Figma 开发的页面模板和样式。
5. 页面只调用领域 Service；Mock、HTTP DTO、Base URL 和 Token 不得进入页面组件。
6. 后端契约变化优先修改 `services/http/`、`api/transport.ts` 和 `api/mappers/`，不得在页面内猜测多个字段名。
7. 公共基础文件和业务页面文件实行交叉审查；跨边界修改必须由对应主责审查。
8. 状态严格区分“Mock 验收”“已适配、待后端”“真实联调通过”。

退出标准：整合分支可稳定构建，且不存在第二套受版本控制的前端应用。

### 阶段 F-I1：认证与公共基础真实验收

1. 使用真实后端验证登录和当前用户。
2. 验证四角色菜单、Router守卫、401和403。
3. 回归登录、控制台、主布局和异常页面。

退出标准：认证主链路和公共基础在真实环境通过。

### 阶段 F-I2：课程与申请联调

1. 联调课程列表和详情。
2. 联调申请创建、列表和详情。
3. 联调主管审批、驳回和HR备案。
4. 补齐契约测试和真实E2E。

退出标准：申请到备案主链路使用真实数据完成，P0/P1缺陷关闭。

### 阶段 F-I3：报名、签到和证书联调

1. 后端契约评审并替换阻塞适配器。
2. 联调报名、取消、签到、缺勤和完成。
3. 联调证书候选、生成、本人查询和详情。
4. 完成四角色全流程回归。

退出标准：完整业务主链路不依赖Mock或手工改库。

## 10. PR和交叉审查规则

- 李司翰必须审查：公共组件、Router、Layout、Auth Store、Axios、权限、环境配置和全局样式。
- 彭浩必须审查：业务页面、业务领域模型、业务 Service、业务 Mapper、Mock流程和业务测试。

- 后端接口变化必须同步 `06-页面接口映射与联调阻塞.md`。

## 11. 验收门禁

每个模块标记“真实联调通过”前必须同时满足：

- 对应后端 Controller、DTO和Swagger/OpenAPI可追踪。
- 页面结构、组件和交互符合Figma基线。
- Mock和HTTP实现遵守同一领域Service接口。
