# 企业内部培训管理系统项目开发规范

## 1. 文档目标

本文档用于统一企业内部培训管理系统的开发协作规则，覆盖：

- 技术架构规范。
- 后端 C# 代码规范。
- Oracle 数据库规范。
- API 接口规范。
- 前端开发规范。
- Git 协作规范。
- 测试、联调和安全规范。

所有成员在开始编码前应先阅读本文档。后续若规范发生变化，需要由组长统一修改，并通知全体成员。

## 2. 总体技术规范

### 2.1 技术约束

- 系统架构：B/S 架构。
- 后端语言：C#。
- 后端框架：建议 ASP.NET Core Web API。
- 数据库：Oracle，部署在云服务器上。
- 前后端协作：以前后端分离 API 为主。
- 接口文档：Swagger / OpenAPI。

### 2.2 推荐目录结构

```text
/
├── src/
│   ├── backend/
│   │   └── TrainingManagement.Api/
│   └── frontend/
│       └── training-management-web/
├── database/
│   └── oracle/
│       ├── V001__init_schema.sql
│       ├── V002__init_sequences.sql
│       ├── V003__seed_data.sql
│       └── README.md
├── document/
│   ├── 数据库设计文档.doc
│   ├── 项目分工计划.md
│   └── 项目开发规范.md
└── README.md
```

### 2.3 模块边界

- 每个后端模块只维护自己的 Controller、Service、Repository、DTO。
- 跨模块访问优先通过 Service 或公开 API，不直接修改其他模块内部代码。
- 数据库结构变更统一交给数据库负责人合并。
- 前端页面可以调用多个模块 API，但不能自行决定关键业务状态。

## 3. API 接口规范

### 3.1 URL 命名

- 统一使用 `/api/{resource}` 前缀。
- 资源名使用小写复数。
- 多个单词使用连字符。
- 状态流转动作放在资源 ID 后。

示例：

```text
GET    /api/employees
GET    /api/employees/{id}
POST   /api/training-requests
PATCH  /api/training-requests/{id}/dept-approve
POST   /api/registrations/{id}/signin
PATCH  /api/certificates/{id}/notify
```

### 3.2 HTTP 方法

| 方法 | 用途 | 示例 |
| --- | --- | --- |
| `GET` | 查询列表或详情 | `GET /api/courses/{id}` |
| `POST` | 新增资源或触发业务动作 | `POST /api/registrations` |
| `PUT` | 完整更新资源 | `PUT /api/trainers/{id}` |
| `PATCH` | 局部更新或状态流转 | `PATCH /api/courses/{id}/publish` |
| `DELETE` | 删除、禁用或逻辑删除 | `DELETE /api/employees/{id}` |

### 3.3 统一成功响应

```json
{
  "success": true,
  "message": "ok",
  "data": {},
  "traceId": "string"
}
```

### 3.4 统一失败响应

```json
{
  "success": false,
  "message": "课程容量已满",
  "errors": [
    {
      "field": "courseId",
      "message": "该课程已达到最大报名人数"
    }
  ],
  "traceId": "string"
}
```

### 3.5 分页响应

```json
{
  "success": true,
  "message": "ok",
  "data": {
    "items": [],
    "page": 1,
    "pageSize": 20,
    "total": 100
  },
  "traceId": "string"
}
```

### 3.6 状态码约定

| 状态码 | 含义 |
| --- | --- |
| `200` | 查询或更新成功 |
| `201` | 创建成功 |
| `400` | 参数错误或业务规则不满足 |
| `401` | 未登录 |
| `403` | 无权限 |
| `404` | 资源不存在 |
| `409` | 数据冲突，例如重复报名、重复证书 |
| `500` | 服务端内部错误 |

### 3.7 常用枚举

后端、前端、数据库脚本应统一枚举含义。推荐接口传输使用英文枚举，前端展示时转换为中文。

| 业务 | 枚举值 | 中文展示 |
| --- | --- | --- |
| 员工状态 | `ACTIVE`, `RESIGNED` | 在职、离职 |
| 课程状态 | `DRAFT`, `PUBLISHED`, `CLOSED` | 草稿、发布、关闭 |
| 申请状态 | `PENDING`, `DEPT_APPROVED`, `DEPT_REJECTED`, `HR_FILED` | 待审批、主管通过、主管驳回、HR 备案完成 |
| 报名状态 | `REGISTERED`, `SIGNED_IN`, `ABSENT`, `COMPLETED`, `CANCELED` | 已报名、已签到、缺勤、已完成、已取消 |
| 测试类型 | `PRE`, `POST` | 训前、训后 |
| 是否值 | `Y`, `N` | 是、否 |
| 黑名单状态 | `ACTIVE`, `RELEASED` | 生效中、已解除 |

如果数据库最终沿用中文状态值，必须由后端统一转换，禁止前端和不同后端模块各自硬编码中文状态。

## 4. 后端 C# 规范

### 4.1 分层结构

```text
TrainingManagement.Api/
├── Controllers/
├── Services/
├── Repositories/
├── Dtos/
├── Entities/
├── Common/
├── Middlewares/
└── Program.cs
```

| 层 | 职责 |
| --- | --- |
| Controller | 接收请求、调用 Service、返回统一响应 |
| Service | 业务规则、状态流转、事务控制 |
| Repository | 数据库访问，不写复杂业务判断 |
| DTO | 接口请求和响应对象 |
| Entity | 数据库表对应实体 |
| Common | 枚举、常量、统一响应、分页对象、工具类 |
| Middleware | 异常处理、日志、认证等中间件 |

### 4.2 命名规范

- 类名、方法名使用 PascalCase，例如 `TrainingRequestService`。
- 私有字段使用 `_camelCase`，例如 `_requestRepository`。
- 异步方法以 `Async` 结尾，例如 `CreateRequestAsync`。
- 接口以 `I` 开头，例如 `ICourseService`。
- DTO 命名规则：
  - 创建请求：`CreateCourseRequest`
  - 更新请求：`UpdateCourseRequest`
  - 查询条件：`CourseQuery`
  - 返回对象：`CourseResponse`

### 4.3 Controller 规范

- Controller 不直接拼 SQL。
- Controller 不写复杂业务判断。
- Controller 不直接返回数据库实体。
- Controller 只负责参数入口、调用 Service、返回统一结果。

示例职责：

```text
EmployeesController
  -> EmployeeService
    -> EmployeeRepository
```

### 4.4 Service 规范

业务规则必须集中写在 Service 层，例如：

- 课程是否允许发布。
- 申请状态是否允许从待审批变为 HR 备案。
- 员工是否在黑名单中。
- 课程是否已满员。
- 签到是否迟到以及扣减多少学时。
- 是否允许生成证书。

涉及多表更新时必须使用事务，例如：

- 创建报名并更新报名统计。
- 签到并更新报名状态。
- 完成培训并生成证书。

### 4.5 Repository 规范

- Repository 只负责数据库读写。
- SQL 参数必须参数化，禁止字符串拼接用户输入。
- 查询方法命名应体现条件，例如 `GetByCourseIdAsync`。
- 写入方法应返回影响行数或新建 ID。
- 不在 Repository 中判断用户权限。

### 4.6 异常与日志

- 业务错误抛出业务异常，由全局异常处理转成统一响应。
- 未知异常返回 500，不把数据库连接串、SQL 细节暴露给前端。
- 关键操作建议记录日志，例如登录、审批、发布课程、生成证书。
- 每个错误响应带 `traceId`，方便定位问题。

## 5. Oracle 数据库规范

### 5.1 对象命名

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 表名 | 大写下划线 | `TRAINING_COURSES` |
| 字段名 | 大写下划线 | `COURSE_ID` |
| 主键约束 | `PK_表名` | `PK_TRAINING_COURSES` |
| 外键约束 | `FK_子表_父表_字段` | `FK_COURSES_TRAINERS_TRAINER_ID` |
| 唯一约束 | `UQ_表名_字段` | `UQ_REGISTRATIONS_EMP_COURSE` |
| 检查约束 | `CK_表名_字段` | `CK_TRAINERS_STAR_LEVEL` |
| 序列 | `SEQ_表名` | `SEQ_TRAINING_COURSES` |

### 5.2 脚本规范

- 所有数据库变更必须写入 `database/oracle`。
- 禁止只在云数据库手工改表而不提交脚本。
- 脚本按版本递增命名。

```text
V001__init_schema.sql
V002__init_sequences.sql
V003__seed_data.sql
V004__add_indexes.sql
```

每个脚本开头写明：

- 用途。
- 作者。
- 日期。
- 是否可重复执行。

### 5.3 表结构规范

- 主键字段统一使用 `NUMBER`。
- 日期字段使用 `DATE` 或 `TIMESTAMP`，全组统一。
- 金额字段使用 `NUMBER(12,2)` 或类似精度。
- 是否字段建议使用 `VARCHAR2(1)`，值为 `Y` 或 `N`。
- 状态字段建议使用英文枚举值。
- 外键字段必须和父表字段类型一致。
- 需要防重复的业务必须建立唯一约束，例如同一员工不能重复报名同一课程。

### 5.4 云数据库安全

- 应用连接使用普通业务账号，不使用 DBA 账号。
- 不把数据库密码提交到 Git。
- 云服务器安全组只开放必要端口。
- 联调前备份数据库。
- 演示前冻结一份可恢复数据。

## 6. 前端开发规范

### 6.1 页面结构

建议页面至少包括：

- 登录页。
- 首页或控制台。
- 员工管理。
- 部门预算管理。
- 黑名单管理。
- 讲师管理。
- 课程管理。
- 培训申请。
- 审批备案。
- 我的报名。
- 签到管理。
- 讲师评分。
- 测试成绩。
- 证书查询。

### 6.2 调用规范

- 所有请求通过统一 API 客户端发送。
- 不在页面组件中散落后端 base URL。
- Token 或 Session 信息由登录模块统一维护。
- 接口返回错误由统一拦截器处理。
- 前端显示中文，接口传输使用统一枚举。
- 表单提交前做基础校验，最终业务校验以后端为准。

### 6.3 页面状态规范

每个列表或表单页面应至少处理：

- 加载中。
- 空数据。
- 提交中。
- 成功提示。
- 失败提示。
- 无权限提示。

### 6.4 权限展示

- 员工可见：课程、我的申请、我的报名、评分、我的证书。
- 部门主管可见：申请审批。
- HR 可见：备案、签到管理、评分复核、测试成绩、证书管理。
- 管理员可见：员工、部门、讲师、课程、角色、黑名单等维护页面。

前端权限只负责展示和体验，真正的权限判断必须由后端完成。

## 7. Git 协作规范

### 7.1 分支规范

建议分支：

```text
main
develop
feature/backend-auth
feature/database-oracle
feature/module-organization
feature/module-course
feature/module-request
feature/module-registration
feature/module-result
feature/frontend-base
feature/frontend-business
```

- `main`：稳定可演示版本。
- `develop`：日常集成分支。
- `feature/*`：个人或模块开发分支。

### 7.2 提交信息

格式：

```text
类型(模块): 简短说明
```

示例：

```text
feat(course): add course publish api
fix(registration): prevent duplicate registration
docs(database): add oracle deployment guide
test(request): add approval workflow cases
```

常用类型：

- `feat`：新增功能。
- `fix`：修复问题。
- `docs`：文档。
- `test`：测试。
- `refactor`：重构。
- `chore`：工程配置或杂项。

### 7.3 合并要求

合并到 `develop` 前必须满足：

- 后端项目能启动。
- 前端项目能启动。
- 数据库脚本可执行。
- Swagger 中新增接口可见。
- 接口字段变更已通知前端。
- 没有提交本地密码、连接串、临时文件。
- 至少一名其他成员完成检查。

## 8. 测试与联调规范

### 8.1 后端接口测试

每个后端模块至少测试：

- 正常新增。
- 正常查询。
- 正常更新或状态流转。
- 参数错误。
- 无权限。
- 数据不存在。
- 重复数据或业务冲突。

### 8.2 前端页面测试

每个业务页面至少检查：

- 页面能打开。
- 列表能加载。
- 表单能提交。
- 错误能提示。
- 刷新后登录态处理合理。
- 无权限用户看不到或不能操作。

### 8.3 主流程联调

最终必须打通以下流程：

1. 管理员创建员工、部门、讲师、课程。
2. 管理员发布课程。
3. 员工提交培训申请。
4. 部门主管审批通过。
5. HR 完成备案。
6. 员工报名课程。
7. HR 或管理员签到。
8. 员工评分。
9. HR 录入测试成绩。
10. HR 生成证书。
11. 员工查看证书。

## 9. 安全与配置规范

- 不提交数据库密码。
- 不提交云服务器账号。
- 不提交个人本地绝对路径配置。
- 连接串放入本地配置文件或环境变量。
- 演示账号密码可以写入文档，但必须是测试账号。
- 后端接口不能把 SQL 错误详情直接返回给前端。
- 管理员接口必须做权限控制。

## 10. 文档维护规范

至少维护以下文档：

- `README.md`：项目启动方式、技术栈、目录说明。
- `document/项目分工计划.md`：人员分工和阶段任务。
- `document/项目开发规范.md`：接口、代码、数据库、Git 规范。
- `database/oracle/README.md`：数据库脚本执行方式。
- 接口说明：可使用 Swagger 作为主文档。

当接口、数据库字段、启动方式发生变化时，相关文档必须同步更新。
