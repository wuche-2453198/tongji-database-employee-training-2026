# 仓库目录结构

## 1. 设计目标

本文档由项目管理与总集成负责人维护，用于统一项目仓库的目录边界，避免不同成员把后端、前端、数据库脚本、文档和临时文件混放。

目录结构设计遵循以下原则：

- 前端、后端、数据库、文档分离。
- 公共配置和启动说明放在固定位置。
- 每个模块负责人只在自己的职责目录内工作。
- 数据库结构变更必须通过脚本进入仓库。
- 不提交本地密钥、真实数据库密码、个人 IDE 缓存和临时文件。

## 3. 一级目录说明

| 路径 | 维护负责人 | 用途 | 说明 |
| --- | --- | --- | --- |
| `README.md` | 项目管理与总集成负责人 | 项目总入口 | 写项目简介、技术栈、目录结构、启动方式、演示账号说明 |
| `document/` | 项目管理与总集成负责人 | 项目文档 | 存放设计文档、分工计划、开发规范、阶段目标等 |
| `src/backend/` | 后端基础架构与认证负责人 | 后端源码入口 | C# ASP.NET Core Web API 项目放在这里 |
| `src/frontend/` | 前端基础与公共页面负责人 | 前端源码入口 | 前端技术栈待定，确定后工程放在这里 |
| `database/oracle/` | Oracle 数据库与云服务器负责人 | Oracle 脚本 | 建表、序列、种子数据、过程、触发器、SQL 示例 |
| `scripts/` | 项目管理与总集成负责人 | 辅助脚本 | 放开发、部署、检查类脚本，不放业务代码 |
| `tests/` | 各测试相关负责人 | 测试材料 | 后端测试、接口测试、联调用例 |
| `tools/` | 项目管理与总集成负责人 | 工具配置 | Postman、Apifox、数据库客户端导出配置等非源码内容 |

## 4. 后端目录建议

后端项目建议采用单个 ASP.NET Core Web API 项目起步，避免课程设计阶段过早拆成多个服务。

```text
src/backend/
├── README.md
└── TrainingManagement.Api/
    ├── TrainingManagement.Api.csproj
    ├── Program.cs
    ├── appsettings.json
    ├── appsettings.Development.json
    ├── Controllers/
    ├── Services/
    ├── Repositories/
    ├── Dtos/
    ├── Entities/
    ├── Common/
    ├── Middlewares/
    └── Properties/
```

### 4.1 后端子目录职责

| 路径 | 内容 | 负责人 |
| --- | --- | --- |
| `Controllers/` | HTTP 接口入口 | 各后端模块负责人 |
| `Services/` | 业务逻辑、状态流转、事务控制 | 各后端模块负责人 |
| `Repositories/` | Oracle 数据访问、SQL 或存储过程调用 | 各后端模块负责人 |
| `Dtos/` | 请求 DTO、响应 DTO、查询 DTO | 各后端模块负责人 |
| `Entities/` | 数据库表对应实体 | 后端基础架构与认证负责人统一规范，各模块补充 |
| `Common/` | 统一响应、分页、枚举、常量、业务异常 | 后端基础架构与认证负责人 |
| `Middlewares/` | 全局异常、认证、日志等中间件 | 后端基础架构与认证负责人 |

## 5. 前端目录建议

前端技术栈目前可以待定，但目录入口先固定为 `src/frontend/`。技术栈确定后，工程放入 `training-management-web/`。

```text
src/frontend/
├── README.md
└── training-management-web/
    ├── package.json
    ├── index.html
    ├── src/
    │   ├── api/
    │   ├── assets/
    │   ├── components/
    │   ├── layouts/
    │   ├── router/
    │   ├── stores/
    │   ├── views/
    │   └── main.*
    └── public/
```

### 5.1 前端子目录职责

| 路径 | 内容 |
| --- | --- |
| `api/` | 后端接口封装 |
| `components/` | 可复用组件 |
| `layouts/` | 主布局、登录布局等 |
| `router/` | 路由配置 |

前端技术栈未定前，前端负责人只需要先维护 `src/frontend/README.md`，说明待定状态、联调方式和后续工程目录。

## 6. 数据库目录建议

Oracle 脚本必须集中放在 `database/oracle/`，禁止只在云数据库手工修改而不提交脚本。

```text
database/oracle/
├── README.md
├── migrations/
│   ├── V001__init_schema.sql
│   ├── V002__init_sequences.sql
│   ├── V003__add_constraints.sql
│   └── V004__add_indexes.sql
├── seed/
│   ├── S001__roles.sql
│   ├── S002__employees.sql
│   ├── S003__courses.sql
│   └── S004__demo_flow.sql
├── procedures/
│   ├── PROC_REGISTER_COURSE.sql
│   ├── PROC_SIGN_IN.sql
│   └── PROC_GENERATE_CERTIFICATE.sql
├── triggers/
│   ├── TRG_DEPT_REMAIN_BUDGET.sql
│   └── TRG_ATTENDANCE_UPDATE_REG.sql
└── samples/
    ├── query_course_registration_count.sql
    ├── query_employee_training_history.sql
    └── query_certificate_status.sql
```

### 6.1 数据库脚本说明

| 目录 | 内容 | 说明 |
| --- | --- | --- |
| `migrations/` | 表结构、序列、约束、索引 | 可从空库初始化结构 |
| `seed/` | 初始数据、演示数据 | 角色、测试账号、课程、完整演示链路数据 |
| `procedures/` | 存储过程 | 报名、签到、证书生成等数据库过程 |
| `triggers/` | 触发器 | 预算维护、签到同步报名状态等 |
| `samples/` | 示例查询 | 汇报和测试时可复用的 SQL |

## 8. 不应提交的内容

以下内容不应进入仓库：

- 真实数据库密码。
- 云服务器账号或私钥。
- 本地 IDE 缓存。
- 编译产物，例如 `bin/`、`obj/`、`dist/`、`node_modules/`。
- 本地日志文件。
- 临时截图和无整理的测试文件。
- 个人数据库客户端配置。

建议 `.gitignore` 至少覆盖：

```text
.DS_Store
.idea/
.vscode/
.vs/
bin/
obj/
node_modules/
dist/
logs/
*.log
*.user
*.suo
appsettings.Local.json
.env.local
```

## 9. README 分工

| 文件 | 维护负责人 | 内容 |
| --- | --- | --- |
| `README.md` | 项目管理与总集成负责人 | 项目简介、技术栈、目录结构、整体启动方式、演示账号说明 |
| `src/backend/README.md` | 后端基础架构与认证负责人 | .NET 版本、依赖安装、连接串配置、启动后端、Swagger 地址 |
| `src/frontend/README.md` | 前端基础与公共页面负责人 | 前端技术栈、依赖安装、启动方式、环境变量 |
| `database/oracle/README.md` | Oracle 数据库与云服务器负责人 | Oracle 版本、脚本执行顺序、Schema、测试数据、备份恢复 |

总 README 是项目入口，不应由各分支分别维护多个版本。模块负责人如果需要写补充说明，应放在对应目录 README 或模块说明中。

## 10. 初始落地顺序

第 0 阶段建议按以下顺序落地目录：

1. 创建 `document/` 并放置项目文档。
2. 创建 `src/backend/` 和后端 README。
3. 创建 `database/oracle/` 及其子目录。
4. 创建 `src/frontend/` 和前端 README。
5. 创建 `tests/api/`，用于后续接口联调。
6. 创建 `.gitignore`，避免无关文件进入仓库。
7. 根目录 README 更新目录结构和维护规则。

## 11. 验收标准

目录结构完成后，应满足：

- 新成员能通过根目录 README 理解项目结构。
- 后端、前端、数据库脚本、文档有明确位置。
- 每个目录有明确维护负责人。
- 数据库变更可以通过脚本追踪。
- 不存在明显的本地缓存、密码、编译产物提交风险。
